# Integration Plan

**Project:** Japan SSW — mmdc-wst  
**Stack:** Express 5 · MongoDB Atlas · AWS S3 · Google OAuth 2.0 · Railway (production) · GitHub Pages (static)

---

| Section | Key Questions | Action Items |
|---------|--------------|--------------|
| **Existing Features Review** | What features in the app could interact with error handling and security measures? | **Features:** CRUD routes for jobs (`jobRoutes.js`), companies (`companyRoutes.js`), users (`userRoutes.js`), applications (`applicationRoutes.js`), admin jobs (`adminJobRoutes.js`), profiles (`profileRoutes.js`). Resume upload to S3 (`profileController.js`). Google OAuth / JWT (`/auth/*`, `backend/src/config/passport.js`). Session cookies (`express-session`). RBAC (`middleware/auth.js` — `protect` / `authorize`). **Security touchpoints:** File upload parsing (multer), JWT verification, session cookies, CORS, CSP (helmet in `app.js`), public static files served from repo root. Audit all routes and document expected error flows for each. |
| **Error Handling** | What types of errors will the app need to handle (e.g., 401 Unauthorized, 404 Not Found)? | **Errors to handle:** 400 validation, 401 missing/invalid JWT, 403 role denied (RBAC), 404 resource not found, 413 payload too large (multer), 415 unsupported media type (resume upload), 422 business rules (duplicate application, invalid enum value), 500 internal server, external service errors (S3 timeout, MongoDB connection, OAuth token failure), rate-limit 429. **Action:** Standardize all error responses to `{"success": false, "error": {"message": "...", "code": "..."}}`. Extend `middleware/errorHandler.js` to map known Mongoose / Multer / AWS errors to correct HTTP status codes. Add structured logging (Winston already installed) with request context — no secrets or PII in logs. |
| **Security with Helmet.js** | Which Helmet.js protections are configured, and for which routes? | **Configured:** `helmet()` applied globally in `backend/src/app.js` with a custom CSP that allows Tailwind CDN, jsDelivr, Google Fonts, and `accounts.google.com`. COOP header set. **Enable / verify:** Tighten CSP by removing `'unsafe-inline'` from `scriptSrc` and replacing with nonces for inline scripts. Enable HSTS in production (`NODE_ENV=production`). Confirm `X-Content-Type-Options`, `Referrer-Policy`, `X-Frame-Options` / `frame-ancestors 'self'`, and `Cross-Origin-Resource-Policy` are active. **Scope:** Apply globally for all web/API routes. Allow relaxed `unsafe-inline` only in local dev (`NODE_ENV !== 'production'`). Document CSP exceptions for Google OAuth popup and CDN resources. |
| **Input Validation** | What inputs are most critical to validate, and what tools will be used? | **Inputs:** Multipart file uploads (type / size), auth tokens, user/profile payloads (`firstName`, `lastName`, `email`, `password`), job/company create-update payloads (`industry`, `japaneseLevel` enums), application submissions (cover letter ≤ 2000 chars), query params and MongoDB ObjectId path params. **Tools & actions:** `express-validator` (already installed) — add route-level validator schemas in `backend/src/validators/`. Server-side MIME/content-type checks in `profileController.js` for resume upload. Replace commented-out `express-mongo-sanitize` with v3 when available, or add a manual sanitize middleware. Reject invalid payloads with 400 + descriptive `error.message`. Validate all ObjectId params to prevent CastError 500s. |
| **Testing for Edge Cases** | What edge cases will be tested (e.g., invalid tokens, unauthorized access, malformed input)? | **Edge cases:** Expired / invalid JWT; missing `Authorization` header; role mismatch (jobseeker accessing employer route); oversized / malformed resume upload; wrong file extension (non-PDF/DOCX); S3 intermittent error / presigned URL expiry; partial upload; duplicate job application (compound unique index); rate-limit triggers; CSP-blocked resources; session fixation; MongoDB ObjectId format errors. **Test plan:** Existing Jest + Supertest suite in `backend/` (`npm test`). Add: unit tests for `middleware/auth.js` protect/authorize; integration tests for S3 upload error path using `aws-sdk-client-mock`; integration tests for Google OAuth callback error paths; Playwright E2E for login redirect and dashboard access. Postman collection (`backend/postman/`) for manual edge-case validation. |
| **Implementation Workflow** | What is the step-by-step order for implementing error handling and security? | 1. Audit all routes in `backend/src/routes/` for missing `protect` / `authorize` middleware and add where absent. 2. Centralize and extend error types in `middleware/errorHandler.js` — map Mongoose, Multer, AWS, and OAuth errors to correct HTTP codes. 3. Add `express-validator` schemas in `backend/src/validators/` and wire to critical routes (auth, jobs, applications, profile). 4. Harden `helmet()` in `backend/src/app.js`: enable HSTS in production, replace `'unsafe-inline'` with nonces, confirm all security headers. 5. Enforce multer file size limits and server-side MIME checks in `profileController.js`. 6. Upgrade or replace `express-mongo-sanitize` and confirm CORS `origin` whitelist covers only `FRONTEND_URL` and Railway domain. 7. Extend Winston logging for S3 / OAuth failures — include `requestId` in log context. 8. Expand Jest / Supertest test suite with edge-case coverage; run `cd backend && npm test` in CI. |
| **Deployment to Railway** | How is the app deployed to Railway, and what must be verified before and after each release? | **Build & start:** Railway uses Nixpacks. Build command: `npm install` (root `postinstall` also runs `cd backend && npm install`). Start command: `node backend/server.js`. Health check path: `/health`. Restart policy: `ON_FAILURE`, max 3 retries (see `railway.json`). **Environment variables required:** `NODE_ENV=production`, `BASE_URL`, `FRONTEND_URL`, `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `GOOGLE_OAUTH_REDIRECT_URI`, `GOOGLE_REDIRECT_URI`, `MONGODB_URI` (Atlas connection string), `JWT_SECRET` (32+ chars), `AWS_REGION`, `AWS_S3_BUCKET_NAME`, IAM role or `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY`. **Pre-deploy checklist:** ① All env vars set in Railway dashboard. ② Google Cloud Console OAuth redirect URIs updated to Railway domain. ③ MongoDB Atlas IP allowlist includes Railway egress IPs (or set to `0.0.0.0/0` with strong auth). ④ `npm test` (Playwright) and `cd backend && npm test` (Jest) pass on branch before merge to `main`. **Post-deploy verification:** Hit `https://mmdc-wst-production.up.railway.app/health` — expect `{"status":"ok"}`. Test Google OAuth login end-to-end. Upload a resume and confirm S3 presigned URL is returned. Check Railway logs for startup errors. **Rollback:** Railway supports one-click rollback to previous deployment from the dashboard. |

## Notes

- All env vars must be set in the Railway dashboard **before** the first deploy — the app will crash on start if `MONGODB_URI` or `JWT_SECRET` are missing.
- Use Railway's **Private Networking** if MongoDB is also hosted on Railway to avoid exposing the DB port publicly.
- The static frontend is also served by the same Railway service (`serve-static` in `backend/server.js`). No separate static hosting configuration is needed unless GitHub Pages deployment is also active.
- For GitHub Pages (static frontend only): the `.github/workflows/` directory contains `playwright-smoke.yml` for CI smoke tests — ensure these pass before tagging a release.
- See [README.md](../README.md#deployment) for Railway environment variable reference and Google Cloud Console redirect URI setup.
